# 06. Passkey (WebAuthn) — 비밀이 움직이지 않는다

지금까지의 모든 방식은 **비밀이 보유자에서 검증자로 이동**했다.
비밀번호도, 세션 ID도, bearer 토큰도 그렇다. 그래서 가로채면 그대로 쓸 수 있었다.

Passkey는 방향이 다르다. **개인키는 인증기를 떠나지 않는다.**
오가는 건 서버가 방금 만든 challenge에 대한 **서명**뿐이다.

여기서 두 가지가 따라 나온다. 비교표에서 이 행이 유일하게 다른 이유다.

- **훔쳐도 쓸모없다** — 서명은 그 challenge 한 번에만 유효하다
- **피싱이 구조적으로 막힌다** — origin이 서명 대상 안에 들어 있다

---

## 실행

**로그인도 하드웨어도 필요 없다.** IdP도 안 쓴다.

```bash
make run-06
```

인증기(휴대폰·보안키) 역할을 하는 40줄짜리 구현체가 들어 있다.
ES256 키페어, 카운터, 그리고 `authenticatorData || SHA256(clientData)` 에 서명하는 능력.
**패스키는 정말 그게 전부다.**

---

## 서버가 저장하는 것

```
저장함    : 공개키, credentialId, signCount
저장 안 함 : 비밀 전부
```

**이 테이블이 통째로 유출돼도 공격자는 아무도 사칭할 수 없다.**
비밀번호 테이블과의 구조적 차이가 이것이다. bcrypt를 아무리 잘 써도
비밀번호 해시는 "깨질 수 있는 비밀"이지만, 공개키는 애초에 공개하라고 만든 값이다.

## 실행 결과

```
등록 완료. credentialId=Z6Vl9p-DhUIcFNBT…
서버가 저장한 것: 공개키 (x=107141845131…)
서버가 저장하지 않은 것: 비밀 전부. 개인키는 인증기를 떠난 적이 없다

정상 로그인    OK 통과 (signCount 2)

공격
  OK 재전송 (가로챈 응답 그대로)          거부  challenge가 내가 낸 값과 다르다
  OK 피싱 (evil.example에서 받은 서명)   거부  origin이 다르다
  OK 다른 사이트의 자격증명              거부  rpIdHash가 다르다
  OK 복제된 인증기 (signCount 정체)      거부  signCount가 늘지 않았다 (3 -> 3)
  OK 남의 개인키로 서명                  거부  서명이 맞지 않다
  OK 등록 응답을 로그인에 재사용          거부  type이 webauthn.create다
```

### 재전송이 왜 안 되나

**진짜 로그인 응답을 통째로 가로채서 그대로 다시 보낸다.** 비밀번호였다면 이걸로 끝이다.

그런데 서버는 매번 새 challenge를 낸다. 가로챈 서명은 **옛날 challenge**에 대한 것이라
새 요청에는 맞지 않는다. 서명이 단발성이라는 게 이 뜻이다.

### 피싱이 왜 구조적으로 막히나

`clientDataJSON`의 `origin`은 **브라우저가 직접 써넣는다.** 페이지의 자바스크립트가
바꿀 수 없다. 그래서 `evil.example`에서 사용자를 속여 서명을 받아내도, 그 서명 안에는
`https://evil.example`이 박혀 있다.

진짜 사이트로 중계해봐야 origin 검사에서 걸린다.
**사용자가 속아도 프로토콜이 안 속는다** — 비밀번호로는 불가능한 성질이다.

### signCount는 복제 탐지용이다

인증기는 서명할 때마다 카운터를 올린다. 키를 복사해가도 **두 복사본이 카운터를 함께
올릴 수는 없다.** 서버가 이미 본 값보다 크지 않으면 복제를 의심한다.

카운터를 항상 0으로 보내는 인증기도 있어서(플랫폼 패스키 다수), 0은 실패로 치지 않는다.
탐지 수단이지 방어벽은 아니다.

## 손으로 짠 것

| 파일 | 하는 일 |
|---|---|
| `internal/webauthn/cbor.go` | CBOR 최소 디코더 (RFC 8949 부분집합) |
| `internal/webauthn/webauthn.go` | 등록·인증 검증, COSE 키 파싱, authenticatorData 해석 |
| `06-passkey/main.go` | 합성 인증기 + 공격 시험 |

**CBOR를 직접 디코딩한 이유**는 라이브러리를 쓰면 볼 게 없어지기 때문이다.
공개키가 결국 **레이블 붙은 정수 두 개**(x, y)라는 걸 보려면 직접 꺼내봐야 한다.

지원하는 것만 처리하고 나머지는 거부한다 — tag도, float도, indefinite-length도 안 받는다.
모르는 걸 조용히 통과시키는 게 파서가 공격면이 되는 경로다.

`authenticatorData`는 고정 레이아웃이다.

```
32바이트  rpIdHash
 1바이트  flags       (UP=0x01 UV=0x04 AT=0x40)
 4바이트  signCount
 나머지   attested credential data (등록 때만)
```

## 비교표에서의 위치

| | 증명 대상 | 훔치면 끝? | 피싱 저항 |
|---|---|---|---|
| 세션·JWT·OIDC | 아는 것 | **예** | **없음** |
| Passkey | 가진 것 (기기) | **아니오** | **있음** |

표 1에서 **처음으로 두 열이 뒤집히는 행**이다.
NIST가 2025년에 피싱 저항 MFA를 의무화하고 passkey를 AAL2로 인정한 이유가 이 두 칸이다.

## 생각해볼 질문

- 개인키가 기기를 안 떠난다면, 기기를 잃어버리면 어떻게 되나?
- 동기화되는 패스키(iCloud·Google 계정)는 "기기를 안 떠난다"는 전제를 깨는 것 아닌가?
- `signCount`를 안 쓰는 인증기가 많다면 복제 탐지는 무슨 의미가 있나?
- attestation을 `none`으로 뒀다. 진짜 attestation은 무엇을 추가로 증명하나? 왜 대부분 안 쓰나?
- 비밀번호 없이 로그인한다면 **계정 복구**는 어떻게 하나? 거기가 새 취약점 아닌가?

## 함정

**하드웨어 없이 검증했다.**
합성 인증기는 실제 기기의 동작을 흉내낸 것이지 기기 자체가 아니다.
검증 로직은 확실히 시험됐지만, 실제 Touch ID나 보안키로 붙여보는 건 별개다.

**`origin`과 `rpId`는 다른 것이다.**
`origin`은 `http://localhost:5562`(스킴·포트 포함), `rpId`는 `localhost`(도메인만).
서명 안에는 `rpId`의 **해시**가 들어가고, `origin`은 `clientDataJSON`에 문자열로 들어간다.
둘 다 검사해야 한다.

**로컬은 예외적으로 HTTP가 허용된다.**
WebAuthn은 secure context를 요구하지만 `localhost`는 예외다.
실제 배포에서는 HTTPS 없이는 아예 동작하지 않는다.
