# 05. JWKS — 서명 검증

02와 04는 둘 다 **"서명은 아직 안 본다"** 는 경고를 달고 있었다.
이 챕터가 그 구멍을 막는다. 새 칸을 채우기보다 **이미 만든 것을 완성**하는 작업이다.

서명이 없으면 나머지 검증은 전부 연극이다.
`iss`·`aud`·`exp`·`nonce`를 아무리 꼼꼼히 봐도, 그 글자를 공격자가 썼다면 의미가 없다.

---

## 실행

**로그인이 필요 없다.**

```bash
make kc-up          # IdP
make run-05
```

두 가지를 한다.

1. **진짜 IdP의 JWKS를 읽는다** — 파서가 실제 프로덕션 IdP에 통하는지 확인
2. **검증기에 위조 토큰을 던진다** — 이쪽은 IdP 역할을 할 RSA 키를 직접 만든다.
   Keycloak의 개인키는 우리에게 없으니, 위조를 증명하려면 이 방법뿐이다

---

## 핵심 규칙 하나

> **알고리즘은 키에서 정한다. 토큰에서 정하지 않는다.**

`alg`는 토큰이 **자기 자신에 대해 하는 주장**이다. 검증기가 그 주장을 읽고
"아, HS256이구나" 하며 분기하는 순간 끝난다.

`internal/jwks`의 허용 목록에는 RSA 서명 알고리즘만 있다.
`none`도 `HS*`도 **애초에 조회되지 않는다.** 분기가 아니라 부재로 막는다.

```go
var allowed = map[string]crypto.Hash{
	"RS256": crypto.SHA256, "RS384": ..., "PS256": ...,
	// none 없음. HS* 없음. 그래서 찾을 수 없다.
}
```

검증 순서도 의도적이다 — **kid로 키를 고르고 → 알고리즘을 대조하고 → 그 다음에야 서명을 계산**한다.
토큰이 검증 방법을 고르는 지점이 한 군데도 없다.

## 실행 결과

```
== 1. 진짜 IdP가 published한 키 ==
   http://localhost:8080/realms/demo/protocol/openid-connect/certs
   kid=IBs-qqOB4Do2aH77xBG3Sa1pet1VB9njnpFcMyvun6Y   alg=RS256  2048비트
   네트워크 호출 1회 (이후 요청은 캐시에서 나간다)

== 2. 검증기 공격 시험 ==
   OK 정상 토큰 (RS256, 올바른 키)             통과
   OK alg: none                              거부   서명이 없다고 주장
   OK alg 혼동 (공개키를 HMAC 비밀로)          거부   허용 목록에 없음
   OK 페이로드 변조 (sub=admin)               거부   서명이 맞지 않음
   OK 모르는 kid                             거부   위조 아니면 롤오버
   OK kid 없음                               거부   어느 키인지 모름
```

### alg 혼동이 왜 무서운가

공격자가 `alg`를 `HS256`으로 바꾸고, **IdP의 공개키를 HMAC 비밀키로 삼아** 서명한다.
공개키는 이름 그대로 공개다. JWKS에서 누구나 가져간다.

검증기가 토큰의 `alg`를 믿으면, 공격자가 아는 값으로 서명한 토큰을 유효하다고 판정한다.
**비대칭 암호가 대칭 암호로 격하되는 순간** 보안이 통째로 사라진다.

## 키 롤오버와 캐시

IdP는 주기적으로 서명 키를 바꾼다. 클라이언트가 키를 캐시만 하고 갱신하지 않으면
롤오버 순간 **전면 장애**가 난다.

그래서 캐시는 **모르는 `kid`를 보면 한 번 다시 가져온다.**
하지만 그게 곧 공격 표면이다 — 아무나 가짜 `kid`를 붙인 토큰을 쏟아부으면
매번 JWKS를 다시 받게 만들 수 있다 (DoS).

그래서 **최소 재조회 간격**을 둔다 (여기선 30초).

```
모르는 kid → 마지막 조회가 30초 이내면 → 거부 (재조회 안 함)
            30초 지났으면          → 한 번 재조회 후 재판정
```

위 출력의 "모르는 kid" 케이스가 이 규칙에 걸려서 거부된 것이다.
캐시가 비어 있었다면 한 번 가져오고 나서 거부됐을 것이다.

## 02와 04가 이제 실제로 검증한다

`internal/oidcclient`에 `Validator`가 생겼고, 서명 검증이 **다른 모든 검증보다 먼저** 돈다.

```go
validator := oidcclient.Validator{
	Issuer: d.Issuer, ClientID: clientID, Leeway: clockLeeway,
	Keys: jwks.New(d.JWKSURI, hc),   // <- 이게 붙기 전엔 nil이었다
}
```

02의 결과 화면에서 `서명` 줄이 **"아직 안 함"에서 "통과"로** 바뀐다.
04의 logout token도 같은 캐시로 서명을 먼저 검증한다 — 그전까지는
형식만 맞으면 남의 세션을 끊을 수 있었다.

`Keys`가 `nil`이면 "검증기가 연결되지 않았다"로 **정직하게 기록**된다. 조용히 건너뛰지 않는다.

## 이 챕터가 채우는 칸

표 1의 `신뢰의 뿌리` 열이 이제 실물이다.
"IdP 서명키 (JWKS)"라고 적혀 있던 게 **실제로 그 키를 가져와 검증하는 코드**를 갖게 됐다.

그리고 03과의 대비가 완성된다.

| | 신뢰의 뿌리 | 확인 방법 |
|---|---|---|
| 세션 (03) | 서버의 map | 조회 — 있으면 유효 |
| OIDC (05) | IdP의 공개키 | 계산 — 서명이 맞으면 유효 |

세션은 **물어봐서** 알고, 토큰은 **계산해서** 안다.
그래서 세션은 즉시 취소되고 토큰은 안 된다. 03에서 본 교환의 뿌리가 여기 있다.

## 함정

**공개키라고 아무 데서나 받아오면 안 된다.**
JWKS URI는 디스커버리 문서에서 오고, 디스커버리 문서는 issuer에서 온다.
그 연결 고리 중 하나라도 평문이면 공격자가 자기 키를 심을 수 있다.

**`kid` 없는 토큰을 "키가 하나뿐이니 그걸로" 처리하고 싶은 유혹**
키가 하나일 때는 동작하고, 롤오버 시작하는 날 조용히 깨진다.
