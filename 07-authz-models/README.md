# 07. 인가 모델 — RBAC / ABAC / ReBAC

여기까지의 모든 챕터는 **"누구인가"** 만 답했다.
**"그래서 뭘 해도 되나"** 는 한 번도 안 다뤘다. 이게 auth의 나머지 절반이다.

같은 시나리오를 세 모델에 각각 통과시켜서, **무엇을 표현할 수 있고 없는지**를 본다.
어느 하나가 이긴다는 얘기가 아니다. **같은 요구사항의 값이 모델마다 다르다**는 얘기다.

---

## 실행

**IdP도 로그인도 필요 없다.**

```bash
make run-07
```

---

## 시나리오

문서 도구 하나. 작지만 **RBAC를 깨뜨리는 요구사항**이 하나 들어 있다 —
"문서 소유자만 수정할 수 있다". 이건 사람에 대한 사실이 아니라 **쌍(pair)에 대한 사실**이다.

---

## 결과

```
alice가 남의 문서를 수정          기대: 거부
  !! RBAC   허용   역할 "editor" 에 "edit" 권한이 있다
     ABAC   거부   소유자가 아니다
     ReBAC  거부   alice 와 salaries 사이에 관계가 없다

alice가 기밀문서를 사무실 밖에서 읽기   기대: 거부
  !! RBAC   허용   역할에 read 권한이 있다
     ABAC   거부   기밀 문서는 사무실 밖에서 못 본다
  !! ReBAC  허용   alice 는 salaries 의 viewer 다

표현하지 못한 것:  RBAC 2건 · ReBAC 1건 · ABAC 0건
```

### RBAC가 갈리는 지점

함수 시그니처에 답이 있다.

```go
func rbac(r request) (bool, string) {
	for _, role := range r.user.roles { ... }   // 문서를 아예 안 본다
}
```

**자원이 판단의 입력이 아니다.** "문서를 수정할 수 있다"까지가 표현의 한계고,
"이 문서를"은 표현할 수 없다.

대신 그 한계가 곧 장점이다 — 판단에 필요한 게 **역할 목록뿐**이라 토큰 클레임에 들어간다.
`realm-demo.json`에 넣어둔 `hr-viewer` 역할이 액세스 토큰의 `realm_access.roles`로
따라오는 게 그래서 가능하다. ABAC·ReBAC는 이렇게 못 한다.

### ReBAC가 갈리는 지점

관계는 저장돼 있지만 **"지금 사무실인가"는 관계가 아니다.**
튜플 `(subject, relation, object)` 어디에도 환경이 들어갈 자리가 없다.

### ABAC가 전부 표현한 대가

요청 시점의 속성을 다 본다. 그래서 유일하게 5건을 다 맞췄다.

대신 **정책이 코드가 된다.** 그리고 판단하는 순간에 필요한 입력이 전부 있어야 한다 —
"사무실인가"를 알려면 그 정보가 요청까지 따라와야 하고, 그게 안 되면 정책이 못 돈다.

---

## 세 모델 요약

| | 판단 입력 | 잘 하는 것 | 못 하는 것 |
|---|---|---|---|
| **RBAC** | 사용자의 역할 | 단순·토큰에 실림 | 자원별 권한 |
| **ABAC** | 주체·자원·동작·환경 속성 | 문맥 규칙 | 단순함 (정책이 코드) |
| **ReBAC** | 주체-자원 관계 튜플 | 소유·공유·"누가 볼 수 있나" | 환경 속성 |

**하나를 고르는 게 아니다.** 실무는 층을 쌓는다 —
거친 정책은 RBAC, 자원 단위는 ReBAC, 문맥 규칙은 ABAC.
위 결과가 왜 그렇게 되는지를 보여준다.

---

## 인증과 인가는 다른 질문이다

| | 질문 | 이 저장소 |
|---|---|---|
| 인증 (authN) | 누구인가 | 표 1~3, 챕터 03~06 |
| 인가 (authZ) | 무엇을 해도 되나 | 표 4, 이 챕터 |

가장 흔한 혼동이 **OAuth를 인증으로 쓰는 것**이다. OAuth는 인가(위임) 프레임워크지
인증이 아니고, 그 틈을 메우려고 OIDC가 나왔다.

한편 OAuth의 `scope`도 인가이긴 하다 — 다만 **거친 인가**다.
"이 앱이 캘린더를 읽어도 된다"까지고, "이 캘린더의 이 항목"은 못 한다.
RBAC가 자원을 못 보는 것과 같은 종류의 한계다. `scope`는
[agent-identity-lab](../../agent-identity-lab)에서 깊게 다룬다.

## 생각해볼 질문

- RBAC에 `document:123:edit` 같은 역할을 만들면 자원별 권한이 되지 않나? 왜 안 하나?
- ReBAC의 튜플이 수백만 개가 되면 "이 문서를 볼 수 있는 사람"을 어떻게 찾나?
- ABAC 정책을 코드가 아니라 데이터로 쓰려면 무엇이 필요한가? (OPA/Cedar가 푸는 문제)
- 인가 결정을 토큰에 넣는 것과 요청 시점에 계산하는 것의 차이는?
  (03에서 본 "상태 위치" 교환과 같은 구조 아닌가?)
- 권한이 바뀌었는데 토큰에 옛 역할이 들어 있다면?

## 함정

**여기 구현은 각 모델의 *모양*이지 프로덕션 엔진이 아니다.**
진짜 ReBAC 엔진(OpenFGA·SpiceDB)은 관계 그래프를 재귀적으로 탐색하고,
진짜 ABAC 엔진(OPA·Cedar)은 정책 언어와 평가기를 갖는다.
여기서는 모델 간 **표현력 차이**만 드러내는 게 목적이다.

**`realm_access.roles`는 실제로 토큰에 들어온다.**
`make run-02` 로 로그인해서 액세스 토큰 클레임을 보면 `hr-viewer`가 있다.
RBAC만이 이렇게 토큰에 얹힐 수 있다는 게 이 챕터의 결론 중 하나다.
