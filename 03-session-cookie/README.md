# 03. 세션 + 쿠키 — 기준선

**IdP 없음. 토큰 없음. 리다이렉트 없음.**
폼 하나, 비밀번호 대조, 난수 ID를 담은 쿠키, 그리고 서버의 map.

이 저장소의 나머지 전부가 **이 방식의 어떤 성질이 부족해서** 나왔다.
그래서 이걸 먼저 만든다. 기준선이 없으면 "왜 OIDC 같은 게 필요한가"를 말할 수 없다.

---

## 실행

Keycloak이 필요 없다. 이 챕터는 IdP 없이 돈다.

```bash
make run-03           # 사이트 A http://localhost:5557
                      # 사이트 B http://localhost:5558
```

`alice` / `alice` 로 로그인한다.

---

## 무엇을 손으로 짰나

| 파일 | 하는 일 |
|---|---|
| `session.go` | 세션 저장소, 난수 ID 생성, 쿠키 속성 |
| `main.go` | 로그인·로그아웃, 비밀번호 대조, 두 사이트 |

**세션 ID는 `crypto/rand` 32바이트다.** 아무 의미도 담지 않은 순수한 조회 키다.
이 방식의 보안 전부가 "이 값을 추측할 수 없다"에 걸려 있다.

**비밀번호는 bcrypt 해시로만 저장한다.** 실습 픽스처에서도 평문을 두지 않는다.
없는 사용자로 로그인해도 해시 대조를 한 번 수행한다 — 안 그러면 응답 시간으로
계정 존재 여부가 새기 때문이다. (요즘 1순위 권장은 Argon2id다. bcrypt를 쓴 건
`$2a$cost$salt+hash` 한 줄에 구성요소가 다 보여서다.)

---

## 이 챕터가 채우는 칸

`notes/comparison.md` 표 1의 첫 줄, 표 3의 첫 줄, 그리고 세션 공격 절.

### 상태 위치 = 서버

브라우저가 들고 다니는 건 의미 없는 ID 하나뿐이다. 사용자가 누구인지는 서버만 안다.
JWT와 정확히 반대다 — JWT는 사용자 정보를 클라이언트 손에 쥐여준다.

이 한 가지 결정이 나머지를 전부 결정한다.

### 취소 = 즉시

`store.destroy(id)` 한 줄. 그 순간 전역으로 끝난다.
**서명된 토큰이 못 하는 일이 이거다.** 토큰은 만료를 기다리는 것 외에 방법이 없다.

### 백채널 호출 = 0회

`make run-03` 하면 로그에 찍힌다. OIDC(00·02)는 3회였다.
IdP가 없으니 서버끼리 오갈 일이 없다. 대신 **모든 인증 부담을 이 앱이 직접 진다** —
비밀번호를 직접 보관하고, 직접 대조하고, 유출되면 직접 책임진다.
그 부담을 남에게 넘기려고 나온 게 OAuth/OIDC다.

---

## SSO: 쿠키는 포트를 구분하지 않는다

사이트 A(5557)에서 로그인한 뒤 사이트 B(5558)를 열어보라. **이미 로그인돼 있다.**

포트가 다른데도 그렇다. 쿠키의 범위는 **도메인**이지 포트가 아니기 때문이다.
이게 공유 도메인 쿠키 SSO의 원리이자, 사람들이 있을 거라 착각하는 경계다.

화면의 "브라우저가 보낸 쿠키"를 보면 Keycloak(`:8080`)의 쿠키까지 섞여 있을 수 있다.
같은 이유다.

> 두 사이트는 같은 세션 저장소를 공유한다. 실무에서 Redis를 공유하는 것과 같은 모양이다.
> 저장소를 공유하지 않으면 쿠키가 전달돼도 상대는 그 ID를 알아보지 못한다.

## 공격 재현: session fixation

**XSS도, 중간자도 필요 없다.** 앱이 로그인 전후로 세션 ID를 그대로 쓰기만 하면 된다.

```bash
make run-03                                       # 방어 모드
make attack-fixation

make run-03 SESSION_FLAGS=-unsafe-no-regenerate   # 취약 모드
make attack-fixation
```

실제 실행 결과:

```
방어 모드                              취약 모드
공격자가 아는 ID : bjeNyejVb7hIni7F…    r_ipBERfimWlD6jm…
로그인 후 ID     : jNVLmKi_rKkLRCxa…    r_ipBERfimWlD6jm…
>>> 막혔다                             >>> 뚫렸다. alice로 로그인된 상태다
```

**두 ID가 같으면 뚫린다.** 공격자는 자기가 아는 ID를 피해자 브라우저에 심어두기만 하면,
피해자가 로그인하는 순간 그 ID가 인증된 세션이 된다.

방어는 한 줄이다 — 로그인 시 **이전 세션을 폐기하고 새 ID를 발급**한다.
로그인만이 아니라 **권한이 바뀌는 모든 순간**(비밀번호 변경, 역할 상승)에 해야 한다.

### 쿠키 속성도 꺼볼 수 있다

```bash
make run-03 SESSION_FLAGS=-unsafe-no-httponly
```

브라우저 콘솔에서 `document.cookie` 를 쳐보라. 세션 ID가 그대로 읽힌다.
`HttpOnly`가 XSS 한 줄과 세션 탈취 사이에 서 있는 유일한 것이다.

## 함정

**앱을 껐다 켜면 전부 로그아웃된다.** 세션이 메모리 map에 있어서다.
"상태 위치 = 서버"의 대가가 이거다. 실무에서 Redis를 쓰는 이유이기도 하다.

**포트가 다르면 다른 사이트라고 착각하기 쉽다.** 쿠키에는 아니다.
격리가 필요하면 도메인을 분리하거나 쿠키 이름/Path를 나눠야 한다.

**`Secure`가 꺼져 있다.** `http://localhost` 라서 켜면 쿠키가 아예 안 실린다.
실제 배포에서는 절대 끄지 않는다.
