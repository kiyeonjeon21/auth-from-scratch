# 00. 레퍼런스 투어 — 완성품 먼저 보기

이 저장소를 **top-down으로** 시작하는 곳이다.

방대한 주제를 밑바닥부터 하나씩 쌓으면 각 조각이 왜 필요한지 모른 채 만들게 된다.
그래서 반대로 간다. **완성된 실물 하나를 먼저 통째로 보고, 거기서 조각을 역으로 뜯는다.**

그 완성품은 이미 여기서 돌고 있다 — **Keycloak.** 장난감이 아니라 실제 프로덕션 IdP다.
`notes/comparison.md`의 거의 모든 행이 Keycloak 안에 이미 기능으로 들어 있다.

---

## 1단계 — 완성품이 뭘 할 수 있는지 본다 (자동)

```bash
make kc-up          # 완성품 기동
make run-tour       # 완성품의 능력을 지도로 뽑는다
```

`capability-map.md`가 생긴다.
이건 **돌아가는 IdP가 자기 입으로 광고하는 능력**을, 비교표의 어느 칸이고 어느 챕터에서 뜯을지 매핑한 것이다.
라이브러리 없이 디스커버리 문서 하나를 GET해서 만든다 — 엔드포인트를 하드코딩하지 않는다는 첫 교훈이 여기 있다.

지도를 읽으면 "인증이라는 게 이만큼이고, 나는 지금 어디쯤이며, 뭘 아직 안 봤나"가 한눈에 잡힌다.

## 2단계 — 완성품이 실제로 동작하는 걸 본다 (라이브러리로)

OIDC 로그인 하나는 [`00-first-login-trace`](../00-first-login-trace)가 이미 완성품 + 라이브러리로
통째로 돌려 와이어까지 캡처해뒀다. 그게 "동작하는 완성품"의 첫 사례다.

나머지 기능(passkey·TOTP·SAML·role)은 **관리 콘솔에서 직접 켜고 눈으로** 본다.
`docker/keycloak/README.md`의 클릭 경로 참고. 지금 realm에는 RBAC용 role이 이미 들어 있다:

- `make kc-up` 후 http://localhost:8080 (`admin`/`admin`) → realm `demo` → Users → alice → Role mapping → `hr-viewer`
- 로그인해서 받은 액세스 토큰을 디코딩하면 `realm_access.roles`에 `hr-viewer`가 보인다 (표 4 RBAC의 실물)

## 3단계 — 하나씩 내려가며 뜯는다 (손으로)

지도의 `어디서 뜯나` 열이 챕터 순서다.
각 챕터는 완성품이 하던 일을 라이브러리 없이 재현하고, `wiretrace`로 완성품과 diff한다.
[`00`→`02`](../02-authcode-pkce)가 이 패턴의 첫 사례다 — 라이브러리 로그인을 손으로 재현하고 트레이스를 비교했다.

```
완성품(Keycloak) 관찰  →  손으로 재현  →  diff로 차이 확인  →  comparison.md 한 칸 채움
```

---

## 완성품 하나로 안 되는 것

Keycloak은 지도의 ~80%다. 나머지는 다른 참조나 개념으로:

| 못 덮는 것 | 어디서 |
|---|---|
| HMAC 요청 서명 (AWS SigV4) | 별도 참조 (표 2) |
| ReBAC (관계 기반 인가) | OpenFGA / SpiceDB (표 4) |
| Verifiable Credential | 개념/읽기만 (표 1) |

`capability-map.md`의 "지도의 가장자리"와 "아직 지도에 없음"이 이 경계를 정직하게 보여준다.

---

## 왜 이 방식인가

AI-native 학습에서 자주 나오는 방식이다 — 완성된 레퍼런스를 먼저 통째로 이해하고,
필요에 따라 각 부분을 파고든다. 인증처럼 넓은 도메인에서 bottom-up이 막히는 이유는
"부품이 왜 있는지 모르고 만들어서"인데, 완성품을 먼저 보면 모든 부품이 맥락을 갖는다.

`capability-map.md`는 그 완성품을 **한 장의 지도**로 압축한 것이고,
이후 모든 챕터는 이 지도의 한 줄을 내려가 뜯는 작업이다.

## 생각해볼 질문

답은 `capability-map.md`와 디스커버리 문서에 있다.

- 디스커버리 문서 하나가 대체한 하드코딩은 몇 개인가? 그 대신 무엇을 신뢰하게 됐나?
- 이 IdP가 광고하는 grant type이 9개다. 그중 이 저장소가 다루는 건 몇 개이고, 왜 나머지는 범위 밖인가?
- `token_endpoint_auth_methods_supported`에 5가지가 있다. 같은 "클라이언트 증명"인데 왜 이렇게 많나?
- 완성품이 광고하지만 우리가 아직 안 본 것(가장자리·아직 지도에 없음) 중, 실무에서 제일 자주 쓰이는 건 뭘까?
