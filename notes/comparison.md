# 방식 비교표

이 저장소의 결과물이다.

**시작은 [`00-reference-tour`](../00-reference-tour)다.** 완성된 실물(Keycloak)이 이 표의 거의 모든 행을
이미 기능으로 갖고 있다. 투어가 그 능력을 한 장의 지도로 뽑아준다. top-down으로 완성품을 먼저 보고,
아래 표의 칸을 하나씩 내려가며 손으로 뜯어 채운다.

챕터 하나를 끝낼 때마다 여기 한 줄이 채워진다.
개별 방식은 다른 데서도 배울 수 있지만, **이 표는 직접 만들어봐야 생긴다.**

빈 칸을 추측으로 채우지 않는다. 구현해서 확인한 것만 적는다.

---

"auth"는 둘이다. **인증(authN, 누구인가)** 과 **인가(authZ, 무엇을 해도 되나).**
표 1~3과 로그아웃·MFA는 인증 쪽이고, 표 4가 인가 쪽이다. 둘은 별개의 질문이라 섞지 않는다.

- **표 1 로그인 방식** — 누구인지 증명하고 로그인 상태를 유지하는 완결된 방법
- **표 2 토큰·요청 보호** — 발급된 토큰을 전송·사용할 때 어떻게 지키나
- **표 3 SSO** — 한 번 로그인을 여러 곳으로 확장하는 방법. SSO는 방식이 아니라 성질이라 별도로 본다
- **표 4 인가 모델** — "누구인지"가 정해진 뒤, "무엇을 해도 되나"를 어떤 규칙으로 판단하나

로그아웃과 MFA는 방식이 아니라 방식 위에 얹는 것이라 표 밖 절로 뺀다.

상태 표기: **완료** (여기서 구현) / **lab** ([agent-identity-lab](../agent-identity-lab)에서 확인) / 빈칸 (미착수)

## 표 1. 로그인 방식

| 방식 | 상태 위치 | 증명 대상 | 훔치면 끝? | 취소 | 신뢰의 뿌리 | 피싱 저항 | 상태 |
|---|---|---|---|---|---|---|---|
| 세션 (서버 저장) | 서버 (map/Redis) | 아는 것 | 예 | **즉시** (map에서 삭제) | 서버 세션 저장소 | 없음 | 완료 (03) |
| 세션 (JWT, 자기완결) | 없음 | 아는 것 | 예 | 어려움 | 발급자 서명키 | 없음 | lab |
| Kerberos | KDC + 티켓 | 아는 것 | 티켓 수명 내 | 어려움 | KDC 대칭키 | 없음 | 읽기만 |
| OIDC 로그인 | IdP + 클라이언트 | 아는 것 | 예 | 부분적 | IdP 서명키 (JWKS, 05에서 검증 구현) | 없음 | 완료 (00·02·05) |
| SAML | IdP + 클라이언트 | 아는 것 | 예 | 부분적 | IdP 서명키 (XML Sig) | 없음 | 읽기만 |
| Passkey (WebAuthn) | 인증기(기기) | 가진 것 (기기) | **아니오** (단발성 서명) | 자격증명 등록 해제 | 기기 개인키 + 서버의 공개키 | **있음** (origin 바인딩) | 완료 (06) |
| Verifiable Credential | 보유자 기기(지갑) | 가진 것 | 아니오 (키 서명) | 발급자 폐기목록 | 발급자 서명 + 지갑 키 | 있음 | 읽기만 (개념) |

빈칸은 아직 구현·확인 안 한 것이다. 추측으로 채우지 않는다.
Passkey의 "피싱 저항 있음"과 "가진 것"만 미리 적은 건, 그게 이 행을 표에 넣는 이유이자
Passkey 챕터에서 실제로 검증할 가설이기 때문이다. 나머지 칸은 만들어보고 채운다.

**Verifiable Credential(VC)** 은 나머지와 신뢰 모델이 다르다.
지금까지는 전부 "검증자가 발급자(IdP)에게 매번 물어보거나 발급자 서명을 확인"하는 구조였다.
VC는 **발급자-보유자-검증자 삼각 구조**다. 발급자가 서명한 자격증명을 보유자가 지갑에 갖고 있다가,
검증자에게 **직접 제시**한다. 검증자는 발급자에게 실시간으로 안 물어본다 (서명만 확인).
그래서 **선택적 공개**(생년월일 대신 "성인임"만 증명)가 가능하다. 이게 지금 인증이 가는 방향이다.
W3C VC Data Model 2.0이 2025년 5월 정식 표준, EU 디지털 신원 지갑이 2026년 롤아웃.
구현은 무거우니 SAML·Kerberos처럼 읽기/개념만.

## 표 2. 토큰·요청 보호

로그인해서 토큰을 받은 다음, 그 토큰을 어떻게 지키나.
표 1의 방식과 직교한다 — OIDC든 세션이든 그 위에 무엇을 얹느냐의 문제다.

| 기법 | 무엇에 묶이나 | 탈취해서 재사용 | 재전송(replay) | 서버 상태 필요 | 상태 |
|---|---|---|---|---|---|
| Bearer | 아무것에도 안 묶임 | 그대로 됨 | 됨 | 불필요 | 완료 (00·02) |
| HMAC 요청 서명 | 공유 비밀 + 요청 내용 | 안 됨 (요청마다 서명) | 막을 수 있음 (nonce/시각) | 불필요 | |
| DPoP | 클라이언트 개인키 | 안 됨 (키 없으면 무용) | 막을 수 있음 | 불필요 | |
| mTLS | 클라이언트 인증서 | 안 됨 | 안 됨 | 인증서 검증 | |

Bearer가 전부 "됨"인 게 핵심이다. 나머지는 그 전제를 하나씩 깨는 방향이다.

## 표 3. SSO는 어떻게 달성되나

SSO는 구현하는 게 아니라 위 방식들이 갖는 성질이다.
"한 번 로그인이 어떻게 여러 곳으로 흐르나"를 방식별로 본다.

| 방식 | SSO를 만드는 것 | 로그아웃 전파 |
|---|---|---|
| 세션 + 공유 도메인 쿠키 | 같은 도메인의 쿠키. **포트는 구분하지 않는다** (03에서 확인) | 쿠키 삭제 + 서버 세션 삭제 (도메인 밖은 안 됨) |
| OIDC | IdP 세션 재사용 (재인증 생략) | **RP-Initiated + back-channel 통지.** 04에서 구현·확인 |
| SAML | IdP 세션 + 각 SP에 assertion | Single Logout(SLO) 프로토콜 |
| Kerberos | TGT 재사용해 서비스 티켓 발급 | 티켓 만료를 기다림 |

00에서 본 "로그아웃했는데 다시 눌렀더니 그냥 들어가진다"가 이 표의 실물이다.
IdP 세션이 살아 있으면 클라이언트가 아무리 자기 세션을 지워도 SSO가 재로그인시킨다.

## 표 4. 인가 모델 (authZ)

여기부터는 인증이 아니라 인가다. "누구인지"가 정해진 뒤 "무엇을 해도 되나"를 판단하는 규칙.
표 1~3과 직교한다 — OIDC로 로그인하든 세션으로 하든, 그 위에 어떤 인가 모델을 얹느냐는 별개다.

| 모델 | 결정 기준 | 유연성 | 복잡도 | 잘 맞는 곳 | 상태 |
|---|---|---|---|---|---|
| RBAC | 역할에 묶인 권한 | 낮음 | 낮음 | 역할이 적고·고정적, 위임 없음 | 완료 (07) |
| ABAC | 사용자·자원·행위·환경 속성 | 높음 | 높음 | 시간·위치·소유 같은 문맥이 중요 | 완료 (07) |
| ReBAC | 주체와 자원의 관계 | 중간 | 중간 | 협업·문서공유·멀티테넌트 SaaS | 완료 (07) |
| scope (OAuth) | 토큰에 실린 거친 권한 목록 | 낮음 | 낮음 | 위임된 API 접근. lab에서 다룸 | lab |

셋은 배타적이지 않다. 실무는 대개 하이브리드로 수렴한다 —
거친 정책은 RBAC, 자원 단위 권한은 ReBAC, 문맥 규칙은 ABAC.
"하나를 고른다"가 아니라 "필요에 따라 층을 쌓는다".

핵심 대비: RBAC는 **미리** 역할을 정해두고(정적 사전분류), ABAC는 요청 **그 순간의** 속성으로 판단한다.

07에서 같은 시나리오 5건을 세 모델에 통과시킨 결과 — 표현하지 못한 건수:

| 모델 | 못 맞춤 | 무엇을 |
|---|---|---|
| RBAC | 2건 | 자원별 권한(소유자만 수정), 환경 조건 |
| ReBAC | 1건 | 환경 조건 (관계가 아니라서) |
| ABAC | 0건 | — 대신 정책이 코드가 된다 |

**RBAC가 자원을 판단 입력으로 받지 않는다**는 게 함수 시그니처에 그대로 드러난다.
그 한계가 곧 장점이기도 하다 — 필요한 게 역할 목록뿐이라 **토큰 클레임에 실린다**.
`realm_access.roles`가 액세스 토큰에 따라오는 게 그래서 가능하고, ABAC·ReBAC는 못 한다.

## 표 밖: 방식 위에 얹는 것

**로그아웃** — 상태를 지우는 연산이지 로그인 방식이 아니다.
어려운 건 상태가 여러 곳에 흩어져 있어서다. **난이도가 상태 위치에 정비례한다** (03·04에서 확인).

| | 상태가 있는 곳 | 로그아웃 |
|---|---|---|
| 세션 (03) | 서버 한 곳 | `destroy(id)` 한 줄. 즉시·전역 |
| OIDC (04) | 브라우저 + RP들 + IdP | 리다이렉트 + 서버 간 통지 프로토콜 |

OIDC 로그아웃은 세 단계다.
1. **로컬만** — 대부분의 앱이 하는 것. IdP 세션이 남아 재로그인 시 비밀번호를 안 묻는다
2. **RP-Initiated** — `end_session_endpoint` + `id_token_hint`. IdP 세션까지 끝낸다
3. **Back-channel** — IdP가 각 RP에 `logout_token`을 POST. 브라우저를 안 거쳐서
   서드파티 쿠키 차단에도 동작한다 (front-channel iframe 방식이 깨진 이유)

`logout_token`은 ID 토큰과 규칙이 다르다 — `events` 클레임 **필수**, `nonce` **금지**.
안 그러면 훔친 ID 토큰으로 남의 세션을 끊을 수 있다. 04에서 위조 4종을 던져 거부를 확인했다.

**MFA (TOTP / 매직링크)** — 2차 요소. 기존 방식 위에 "받는 것" 증명을 하나 더 얹는다.
그 자체로 로그인 방식이 아니라 어느 방식에든 붙일 수 있는 강화다.

**세션 계층 공격** — 세션(서버) 챕터의 공격 재현 재료. OWASP가 정리한 근본 함정들이다.

| 공격 | 원리 | 막는 법 |
|---|---|---|
| Session fixation | 로그인 후에도 로그인 전 세션 ID를 그대로 쓰면, 공격자가 심어둔 ID로 세션 탈취. **03에서 실제로 재현함** (`make attack-fixation`) | **로그인·권한변경 때마다 세션 ID 재발급** |
| CSRF | 남의 사이트에서 내 쿠키로 요청을 위조 | `SameSite` 쿠키 + CSRF 토큰 (세션에 바인딩) |
| 토큰 저장 위치 | 액세스 토큰을 localStorage에 두면 XSS 한 줄로 탈취 | httpOnly 쿠키 (JS가 못 읽음) 또는 BFF |
| 쿠키 속성 누락 | Secure 없으면 평문 전송, HttpOnly 없으면 JS 노출 | `HttpOnly; Secure; SameSite` 셋 다 |

**인증 강도 (NIST AAL)** — "어떤 방식"이 아니라 "얼마나 강한가"의 척도. 표 1의 `피싱 저항` 열과 엮인다.

| 등급 | 요구 | 표 1에서 |
|---|---|---|
| AAL1 | 단일 요소 (비밀번호) | 세션·OIDC(비번만) |
| AAL2 | MFA. **피싱 저항 syncable passkey 포함** | passkey, MFA 얹은 방식 |
| AAL3 | 하드웨어 기반 + 검증자 위장 저항 | 하드웨어 보안키 |

2025년 NIST가 연방기관에 피싱 저항 MFA(WebAuthn/FIDO2)를 의무화하고 passkey를 AAL2로 인정했다.
"피싱 저항이 있다/없다"가 규제 등급으로 굳어지는 중이라는 뜻이다.

## 각 방식을 채울 때 답할 질문

빈 행을 채울 때마다 먼저 답한다. 답이 안 나오면 아직 이해 못 한 것이다.

- **앞의 무엇이 부족해서 이게 나왔나?** 인증의 역사는 "이게 깨져서 저게 나왔다"의 연속이다.
- **무엇을 포기했나?** 공짜는 없다. 상태를 버리면 취소를 잃고, 취소를 얻으면 확장성을 잃는다.
- **여기서 훔칠 수 있는 값은 무엇이고, 훔치면 무엇을 할 수 있나?**

## 지금까지 확인한 것

**서버가 기억하면 취소가 공짜, 확장이 비싸다 (03)**
세션 챕터를 만들어보니 대가가 선명하다.
`store.destroy(id)` 한 줄로 즉시·전역 무효화가 된다. 서명된 토큰은 이걸 못 한다.
대신 앱을 껐다 켜면 전원 로그아웃되고, 서버를 늘리면 저장소를 공유해야 한다.
**"상태를 어디에 두나"가 취소와 확장 사이의 교환**이라는 게 표 1 첫 줄의 의미다.

**백채널 0회의 양면 (03)**
세션 로그인은 서버 간 호출이 한 번도 없다. OIDC(00·02)는 3회였다.
단순하다는 뜻이기도 하지만, **비밀번호를 이 앱이 직접 보관하고 직접 책임진다**는 뜻이기도 하다.
그 부담을 IdP에 넘기려고 나온 게 OAuth/OIDC다. 왕복이 늘어난 건 부담을 옮긴 값이다.

**"취소가 공짜"는 상태가 한 곳에 있을 때만 참이다 (03 → 04)**
03에서 로그아웃은 map 삭제 한 줄이었다. 04에서 IdP가 끼자 같은 일이
리다이렉트 + 서버 간 통지 프로토콜이 됐다. 상태를 분산시킨 대가가 여기서 청구된다.
**분산되는 순간 취소는 한 줄이 아니라 프로토콜이 된다.**

**쿠키는 포트를 구분하지 않는다 (03)**
5557에서 로그인하면 5558도 로그인 상태다. 쿠키 범위는 도메인이지 포트가 아니다.
공유 도메인 SSO가 되는 원리이자, 있을 거라 착각하는 경계다.

**비밀의 이동 방향이 모든 걸 가른다 (06)**
비밀번호·세션ID·bearer 토큰은 전부 **보유자 → 검증자**로 이동한다. 그래서 가로채면 재사용된다.
Passkey는 개인키가 움직이지 않고 **서명만** 간다. 그 서명은 서버가 방금 낸 challenge에 묶여 있어
단발성이고, `origin`이 서명 대상 안에 들어 있어 피싱 사이트가 받아낸 서명은 진짜 사이트에서 쓸 수 없다.
**사용자가 속아도 프로토콜이 안 속는다** — 표 1에서 처음으로 `훔치면 끝?`과 `피싱 저항` 두 열이 뒤집힌다.
재전송·피싱·다른 사이트·복제·남의 키·등록응답 재사용 6종을 던져 전부 거부를 확인했다.

**서버가 저장하는 게 비밀이 아니다 (06)**
Passkey 서버는 공개키만 갖는다. **그 테이블이 통째로 유출돼도 누구도 사칭할 수 없다.**
bcrypt를 아무리 잘 써도 비밀번호 해시는 "깨질 수 있는 비밀"이지만, 공개키는 공개하라고 만든 값이다.

**인가는 인증과 다른 질문이고, 모델마다 표현력이 다르다 (07)**
같은 시나리오 5건에서 RBAC는 2건, ReBAC는 1건을 표현하지 못했다.
RBAC는 자원을 입력으로 안 받아 "소유자만 수정"을 못 쓰고, ReBAC는 환경 속성을 관계로 표현할 수 없다.
ABAC만 전부 표현했지만 정책이 코드가 되는 값을 치른다.
**하나를 고르는 게 아니라 층을 쌓는 이유**가 이 결과다.

**bearer 토큰의 대가**
JWT와 OIDC 액세스 토큰은 둘 다 bearer다. 가진 사람이 곧 주인이라 훔치면 그대로 쓸 수 있고,
자기 완결적이라 만료 전에 죽이기가 어렵다. 수명을 짧게 잡는 것 말고는 방어가 없다.
표 2의 DPoP/HMAC/mTLS가 이 전제를 깨는 방향이다.

**`aud` 없는 액세스 토큰**
Keycloak 기본 설정은 액세스 토큰에 `aud`를 넣지 않는다 (00 발견 2번).
리소스 서버가 토큰만 보고는 자기 것인지 판단할 수 없다는 뜻이다.

**서명을 안 보면 나머지 검증이 전부 무의미하다 (02 → 05에서 해결)**
02·04는 `iss`/`aud`/`exp`/`nonce`를 다 검증하면서도 서명은 안 봤다.
05에서 JWKS 검증을 붙여 그 구멍을 막았고, 이제 서명이 **다른 모든 검증보다 먼저** 돈다.
검증 순서에는 위계가 있다.

**알고리즘은 키에서 정한다, 토큰에서 정하지 않는다 (05)**
`alg`는 토큰이 자기 자신에 대해 하는 주장이다. 그걸 믿고 분기하면 alg 혼동으로 뚫린다 —
공격자가 IdP의 **공개키를 HMAC 비밀로** 삼아 서명하면, 비대칭이 대칭으로 격하된다.
허용 목록에 RSA 서명만 두어 `none`과 `HS*`가 **조회조차 안 되게** 막았다.
위조 6종(none / alg혼동 / 페이로드변조 / 모르는 kid / kid없음 / 정상)을 던져 확인했다.

**신뢰의 뿌리: 물어보기 vs 계산하기 (03 ↔ 05)**

| | 신뢰의 뿌리 | 확인 방법 |
|---|---|---|
| 세션 (03) | 서버의 map | 조회 — 있으면 유효 |
| OIDC (05) | IdP의 공개키 | 계산 — 서명이 맞으면 유효 |

세션은 물어봐서 알고 토큰은 계산해서 안다. **그래서 세션은 즉시 취소되고 토큰은 안 된다.**
03에서 본 "취소 vs 확장" 교환의 뿌리가 여기 있다.

**키 롤오버는 캐시와 DoS 사이의 줄타기 (05)**
모르는 `kid`에 재조회를 안 하면 롤오버 때 전면 장애, 매번 하면 가짜 kid로 DoS.
최소 재조회 간격(30초)이 그 사이의 타협이다.

**라이브러리가 해주던 일은 대부분 왕복이 아니라 계산이었다**
00(라이브러리)과 02(손으로)의 트레이스를 비교하니 네트워크 차이가 딱 하나였다.

```
백채널 호출:  00 = 3번,  02 = 2번
없어진 것:    JWKS 가져오기
```

`state`/`nonce` 생성, PKCE 해시, 폼 조립, 클레임 대조는 전부 네트워크에 안 남는다.
그래서 트레이스만 보면 두 챕터가 거의 같아 보이는데 코드 양은 전혀 다르다.
**와이어 캡처로 볼 수 있는 것과 볼 수 없는 것의 경계**를 보여주는 사례다.
앞으로 다른 방식을 비교할 때도 트레이스가 같다고 같은 게 아니라는 걸 기억할 것.
