# 04. 로그아웃 — SSO의 진짜 어려운 부분

챕터 03에서 로그아웃은 **한 줄**이었다. `store.destroy(id)`.

IdP가 끼는 순간 그게 안 된다. 로그인 상태가 **세 곳**에 흩어지기 때문이다.

```
브라우저 쿠키   ← 우리가 지울 수 있다
이 앱의 세션    ← 우리가 지울 수 있다
IdP의 SSO 세션  ← 우리 것이 아니다
```

앞의 둘만 지우면 앱은 로그아웃된 것처럼 보인다. 그런데 로그인을 다시 누르면
**비밀번호도 안 묻고 그대로 들어가진다.** 세 번째가 살아 있어서다.

챕터 00의 발견 3번(손등 도장)에서 이미 본 현상이다. 이제 그걸 고친다.

---

## 실행

```bash
make kc-up        # IdP 필요
make run-04       # RP A http://localhost:5560
                  # RP B http://localhost:5561
```

RP가 **둘**인 이유는 세 번째 문제 때문이다 — A에서 로그아웃하면 B는 그걸 어떻게 아는가.

---

## 세 가지 로그아웃을 직접 눌러보기

### 1. 로컬만 (`/logout-local`) — 대부분의 앱이 하는 것

우리 세션과 쿠키만 지운다. 화면은 로그아웃됐다고 나온다.

**다시 로그인을 눌러보라. 비밀번호를 안 묻는다.**
IdP 세션이 살아 있어서 조용히 재로그인된다. 공용 PC에서 이게 왜 문제인지는 명백하다.

### 2. RP-Initiated (`/logout-rp-initiated`) — 진짜 로그아웃

브라우저를 IdP의 `end_session_endpoint`로 보낸다.

```
GET {end_session_endpoint}
      ?id_token_hint=...            어느 세션을 끝낼지 + 물어볼 자격 증명
      &post_logout_redirect_uri=... 끝나면 돌려보낼 곳 (사전 등록 필수)
      &state=...
```

`id_token_hint`가 없으면 IdP는 "정말 로그아웃할까요?" 확인 화면을 띄워야 한다.
누가 남의 세션을 임의로 끊는 걸 막기 위해서다.

이번엔 다시 로그인하면 **비밀번호를 묻는다.** IdP 세션까지 끝났기 때문이다.

### 3. Back-channel — 다른 RP는 어떻게 아나

A에서 2번을 누르면, IdP가 **같은 세션에 참여한 모든 RP에게** 서버 대 서버로 통지한다.

```
POST /backchannel-logout
Content-Type: application/x-www-form-urlencoded

logout_token=eyJ...
```

브라우저가 전혀 관여하지 않는다. **이게 핵심이다** — 옛날 방식인 front-channel은
IdP가 각 RP의 로그아웃 URL을 iframe으로 열었는데, 요즘 브라우저의 서드파티 쿠키 차단에
막혀서 조용히 실패한다. back-channel은 그 문제가 없다.

A에서 로그아웃한 뒤 B를 새로고침해보라. B도 로그아웃돼 있다.

---

## `sid` — 통지를 세션에 연결하는 열쇠

back-channel 통지는 "세션 X가 끝났다"고만 알려준다. 그게 **우리 세션 중 어느 것인지**
알려면 로그인할 때 미리 연결해둬야 한다.

그래서 이 앱은 ID 토큰의 `sid`(IdP 세션 식별자)를 저장한다.

```go
p.sess[s.ID] = s        // 우리 세션 ID -> 세션
p.bySID[s.Sid] = s.ID   // IdP의 sid -> 우리 세션 ID
```

`sid`를 안 챙겨두면 통지를 받고도 아무것도 못 한다. 화면에 `sid`를 띄워두었으니
로그인할 때 확인하고, 로그아웃 로그의 `sid`와 같은지 보라.

---

## logout token은 ID 토큰이 아니다

둘 다 IdP가 서명한 JWT지만 규칙이 다르다. 이 차이가 곧 방어다.

| | ID 토큰 | logout token |
|---|---|---|
| `events` 클레임 | 없음 | **필수** |
| `nonce` | 있음 | **있으면 안 됨** |
| 용도 | "이 사람이 누구다" | "이 세션이 끝났다" |

`events`가 필수인 이유: 없으면 공격자가 **훔친 ID 토큰을 로그아웃 엔드포인트에 던져서**
남의 세션을 임의로 끊을 수 있다. `nonce` 금지도 같은 이유의 반대 방향이다.

실제로 위조 4종을 던져 검증했다.

```
정상 형태                          -> 200
events 클레임 없음 (ID 토큰 대용)   -> 400  거부
nonce 있음                        -> 400  거부
다른 RP용 토큰 (aud 불일치)         -> 400  거부
JWT 형식 아님                      -> 400  거부
```

> 서명은 아직 검증하지 않는다. JWKS가 필요하고 그건 다른 챕터다.
> 지금 상태로는 **서명 없이 위 조건만 맞춘 토큰도 통과한다.** 실제 배포에서는 치명적이다.

---

## 이 챕터가 채우는 칸

표 3(SSO)의 `로그아웃 전파` 열, 그리고 로그아웃 절.

핵심은 **로그아웃 난이도가 상태 위치에 비례한다**는 것이다.

| | 상태가 있는 곳 | 로그아웃 |
|---|---|---|
| 03 세션 | 서버 한 곳 | `destroy(id)` 한 줄 |
| 04 OIDC | 브라우저 + RP들 + IdP | 리다이렉트 + 서버 간 통지 프로토콜 |

챕터 03에서 "취소가 공짜"라고 했던 게 **한 곳에 모여 있을 때만** 참이었다.
분산되는 순간 취소는 프로토콜이 된다.

---

## 생각해볼 질문

답은 코드와 화면 로그에 있다.

- 로컬 로그아웃만 하고 다시 로그인했을 때 비밀번호를 안 묻는 게, 버그인가 사양인가?
- `id_token_hint` 없이 `end_session_endpoint`를 호출하면 IdP는 왜 확인 화면을 띄우나?
- `post_logout_redirect_uri`를 사전 등록하지 않으면 어떤 공격이 가능한가?
- RP가 10개인데 하나가 통지를 못 받으면(서버 다운) 로그아웃은 성공인가 실패인가?
- back-channel 통지는 브라우저를 안 거친다. 그럼 **그 브라우저의 쿠키**는 누가 지우나?
- front-channel logout이 서드파티 쿠키 차단으로 깨진다면, 왜 아직 스펙에 남아 있나?

---

## 함정

**`host.docker.internal`**
IdP는 Docker 안에서 돌고 RP는 호스트에서 돈다.
back-channel 통지 URL에 `localhost`를 쓰면 **컨테이너 자기 자신**을 가리켜서 통지가 안 온다.
`realm-demo.json`에 `http://host.docker.internal:5560/backchannel-logout` 으로 등록한 이유다.
같은 네트워크에서 실제로 도달하는지 확인했다.

**로컬 로그아웃은 "성공한 것처럼" 보인다**
에러도 안 나고 화면도 로그아웃 상태다. 그래서 실무에서 이 버그가 오래 산다.
테스트로 잡으려면 "로그아웃 후 재로그인 시 자격증명을 묻는가"를 확인해야 한다.

**서명 미검증**
logout token의 서명을 안 본다. 형식만 맞으면 통과한다.
JWKS 챕터 전까지는 이 앱을 로컬 밖에 두면 안 된다.
